# Nool System Overview

This document provides a technical introduction to Nool for developers joining the project.

## What Nool Does

Nool is an enterprise knowledge assistant. It allows employees to ask questions about internal documents—such as HR policies, IT guides, and company procedures—and receive accurate, cited answers generated by a local language model using verified evidence passages.

## Who Uses It

- **Employees**: Team members seeking rapid, reliable answers about workplace policies, technical setups, and operational processes.
- **System Administrators & Knowledge Managers**: Operators who maintain document collections, manage access policies, update indexes, and verify evidence accuracy.

## What Problem It Solves

Enterprise documentation is often dispersed across multiple repositories, wikis, and file shares. Finding relevant passages manually is slow, and generic AI solutions risk hallucinating information, exposing confidential content to unauthorized users, or answering from outdated revisions. Nool solves these issues by:
- Grounding answers strictly in retrieved evidence with exact source citations.
- Enforcing role-based access checks so employees only see authorized material.
- Verifying document currency so deprecated policies are not presented as active.
- Running models locally to keep enterprise data private.

## How a Question Moves Through the System

When fully implemented, a query traverses the following lifecycle:

1. **User Submission**: The user submits a question via the Streamlit interface.
2. **Security & Context Evaluation**: The user's role and identity are attached to the query context.
3. **Hybrid Retrieval**:
   - BM25 performs sparse keyword matching.
   - Contriever performs dense semantic matching across document passages.
   - Candidate passages are merged and ranked.
4. **Evidence Validation & Filtering**:
   - Access permissions are checked: passages exceeding the user's role authorization are pruned.
   - Freshness checks confirm the source document version is currently valid.
5. **Evidence Memory Lookup & Storage**:
   - The system checks an HNSW index and SQLite store for existing verified evidence.
   - Valid new evidence is indexed for future queries.
6. **Answer Generation**:
   - The validated evidence passages and user query are formatted into a prompt.
   - A local Qwen language model generates an answer with explicit citations.
7. **Response Delivery**:
   - The UI presents the answer alongside collapsible reference cards showing the cited passages and source document metadata.

## Major Components

- **`nool.config`**: Centralized configuration management, environment validation, and path resolution.
- **`nool.data`**: Ingestion pipelines, document chunking, manifest recording, and dataset preparation.
- **`nool.retrieval` (Planned)**: Hybrid search orchestrator coordinating lexical search (BM25) and dense embeddings (Contriever).
- **`nool.evidence` (Planned)**: Evidence store managing candidate passage caching, HNSW vector indexing, and SQLite metadata.
- **`nool.security` (Planned)**: Permission enforcement mechanisms matching document access control lists (ACLs) against user attributes.
- **`nool.generation` (Planned)**: Prompt construction, local Qwen model loading, inference execution, and citation formatting.
- **`nool.evaluation` (Planned)**: Offline benchmark runners computing retrieval recall, MRR, citation precision, and answer faithfulness.
- **`nool.app` (Planned)**: Streamlit web interface for interactive search, answer inspection, and administration.

## Document Updates and Access Permissions

### Document Freshness and Updates
Internal policies change over time. When source documents are updated or superseded:
- The data ingestion pipeline indexes new revisions with incremented version tags and timestamps.
- Deprecated revisions are flagged as inactive in the metadata database.
- Retrieval filters exclude inactive documents, preventing stale evidence from being used during answer generation.

### Access Permissions
Not all employees possess identical access rights. Security is enforced as an integral retrieval constraint:
- Every document chunk carries an access control list (ACL) designating required roles or departments.
- At query time, the security module filters candidate evidence against the authenticated user's permissions prior to generation.
- Passages failing access checks are discarded, ensuring unauthorized text never enters model context or user responses.
